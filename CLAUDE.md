# FotoHu — как здесь работать

Семейный бот-архиватор фотографий. Пользуется им семья, а не разработчики:
любая ошибка здесь — это не упавший сервис, а потерянный снимок.

## Кто за что отвечает

Владелец проекта (`dima.username@gmail.com`) ставит задачи и принимает
результат. Он не программист и намеренно не работает с GitHub: ему нужен
работающий бот, а не инструкция, куда нажать.

Отсюда рабочая договорённость, которую он дал явно:

- **Мержить в `main` — твоя работа.** Проверка `test` зелёная на текущем
  коммите, конфликтов нет — мержи сам, не спрашивая.
- **Спрашивай, когда в изменении есть миграция базы** (`src/fotohu/db/migrations/`).
  База — это архив семьи; необратимое изменение согласовывается.
- **Спрашивай, когда сам не уверен.** Неуверенность — нормальный повод
  остановиться; «на всякий случай» — нет.
- Выкатку на боевую машину делает не бот, а человек или браузерный агент —
  готовь для этого точную последовательность команд, а не намёки.

## Перед каждым пушем

```bash
.venv/bin/ruff check src tests
.venv/bin/python -m pytest -q
```

То же самое гоняет CI (`.github/workflows/ci.yml`) на Python 3.11 — той же
версии, что в `Dockerfile` и на боевой машине.

## Боевая машина

Google Cloud, проект `fotohu-507615`, единственная VM `fotohu` в зоне
`us-central1-a` (e2-micro, 1 ГБ памяти). Каталог `~/fotohu`, Docker Compose,
`COMPOSE_FILE` уже включает `docker-compose.prod.yml`. Обновление:

```bash
cd ~/fotohu && git pull --ff-only && docker compose up -d --build
```

`--build` обязателен: код запекается в образ, том с ним не подключается.
Миграции накатываются сами при старте.

Перед запуском стоит посмотреть, что именно приехало, и снять копию базы:

```bash
cd ~/fotohu && git fetch origin main && git diff --stat HEAD origin/main
docker compose cp bot:/data/fotohu.sqlite3 ~/backup-fotohu-$(date +%F-%H%M).sqlite3
```

Код можно катить не глядя — для того и CI. А вот `docker-compose*.yml`,
`Dockerfile` или `Caddyfile` в этом списке означают, что меняется устройство
самой машины: тома, порты, лимиты памяти. Такое читают до запуска, а не после.
Время в имени бэкапа — чтобы второй деплой за день не затёр копию от первого.

Что помнить об этой машине: **1 ГБ памяти и `mem_limit: 512m` на бота.**
Всё, что декодирует картинки или держит файл в памяти, проверяй на пик RSS —
там, где на ноутбуке «ну лишние 400 МБ», здесь контейнер убивают.

## Правила самого проекта

- **Оригинал неприкосновенен.** Байты, присланные документом, доезжают до
  облака без изменений; EXIF читается, но никогда не переписывается.
- **Удалять из чата только после проверенной копии.** Этот порядок — главное
  свойство проекта, его нельзя «оптимизировать».
- Комментарии и docstring'и в коде — по-английски, тексты бота — в
  `src/fotohu/i18n/` (русский основной, английский — запасной).
- Весь SQL живёт в `src/fotohu/db/repo.py`, миграции — отдельные файлы
  `NNN_*.sql`, только добавляющие.
- Ограничения мессенджеров описаны в `docs/limitations.md` — прежде чем
  обещать функцию, проверь, что Telegram или Viber её вообще позволяют.
